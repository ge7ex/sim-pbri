# Phase F — Simulator / Asset

Simulator Type and Simulator Asset are separate from the quantity-based SimResource catalog. Both belong to a College; a composite foreign key prevents an Asset from belonging to a Type in another College. Assets are durable individual items, with no delete workflow. Maintenance records are append-only and retain actor and timestamps. Asset/type updates retain previous values and actor in the audit table.

A Booking may select one Asset or none, preserving existing bookings. Active Asset and active Type are required for new requests and approval. The existing BookingAvailabilityResolver handles Pending and Approved occupancy with the same half-open overlap semantics as resources. Resource rows are locked first, followed by the Asset and Type rows inside create/approve transactions. Management updates lock existing Asset before Type; status and ownership are rechecked under the Asset lock. Scenario Type recommendations are optional and never constrain the selected Asset.

Financial inputs are either all omitted or a complete purchase year (Gregorian), price and useful-life trio. Depreciation is an estimate by calendar year: straight line, zero residual value, no depreciation in the purchase year; elapsed years are capped at useful life. Integer cents and half-up rounding are used, with accumulated depreciation computed directly instead of multiplying rounded annual amounts. Values are computed, not persisted. This is not an accounting ledger or an approved institutional accounting policy. A different policy can replace the service without changing bookings.

Admin manages own-college data, financial fields and maintenance notes. Staff can read operational data and maintenance history without costs or administrative notes. Lecturer has no management access; Booking payloads explicitly allowlist operational fields for every role and never serialize asset financials or maintenance records.

Schema changes are additive. Down migrations require first removing booking links; there is no physical asset/type deletion endpoint. Verification uses isolated SQLite testing data and disposable browser QA data. Local runtime migration uses the configured development database after checking pending migrations.

Concurrency invariant: every occupancy-producing transaction acquires resource, Asset and Type locks before its first nonlocking availability query. The Asset lookup itself is a locking read. This prevents a REPEATABLE READ snapshot from being established before waiting for a competing reservation. Create, approval and recall share this order; existing asset management uses Asset then Type. Type-only updates do not acquire Asset locks.
